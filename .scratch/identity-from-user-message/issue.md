# recall：身份只从用户消息读，不认宿主 runtime-context

Status: ready-for-agent

## 用户故事

作为在 DSH 里用 `/recall <名字>` 指派 agent 的用户，我想要 AI 认我打出的那个名字，
以便它的读写在正确的记忆区，而不是所有会话都堆进 `lead` 区。

## 背景 / 为什么要变

用户连续几轮说 `/recall 开编`，AI 却把日记全写进了 `lead` 记忆区。

**硬证据**：该轮 lead 区收到 3 篇日记，kaibian 区 0 篇；开编的检索留痕停在 11:31，
之后到收工一次都没被调用。

**追溯链（不变量 5）**：身份机制不是本轮才有。提交 `0d78a8c`（2026-09-03，
标题「身份优先记忆路由 + 身份即开户」）就已写入 SKILL.md：

> **声明身份**：会话开始时识别本 AI 的角色名

这一段要保护的原始意图是**隔离墙**——"绝不让语义猜库戳破记忆隔离墙"。
它一直是好的设计，本轮不推翻它。

**根因在这句话的歧义**，不在机制缺失：

| 原文 | 被读成 |
|---|---|
| 「识别**本 AI 的**角色名」 | 去看我自己叫什么（→ 读到宿主注入的 `lead`） |
| 「身份是**会话持有者**声明的事实」 | 身份在宿主那边，已定好 |

AI 因此去读宿主注入的 `runtime-context`，里面写死：

```
You are the root agent. Your name is "lead".
```

**这是宿主 agent 树内部的地址簿**（`dsh-subagent/src/names.ts:13`，
`export const ROOT_AGENT_NAME = 'lead'`），只用于 `send_message` 寻址与
`list_agents` 显示。它与 recall 的记忆区**没有代码关联**——搜遍宿主源码，
没有一处提到 `midnight` / `recall`。两个 `lead` 重名纯属巧合。

**并发现象**：该时段有 5 个并行会话，其中 3 个都以 `/recall <名字>` 开头
（开编 ×2、量量 ×1），全部没换指针，全部写进 `lead` 区。同一个 `recall.db`
被多方并发写入。

## 范围外（本轮不做）

- 不改宿主 `@deepseek-ai/dsh-*` 任何包（`ROOT_AGENT_NAME` 写入 node_modules，升级即丢）
- 不改 recall 任何 `.py` 运行时逻辑（机制本来就对，错的是文档表述）
- 不清理已混入 lead 区的历史数据（另议）
- 不处理其他并行会话（各自下次 `/recall` 时自动生效）
- 不加"每条回复报身份"这类运行时开销
