## 路径可移植性：三级判据

| 档 | 例子 | 该写成 |
|---|---|---|
| `inside` | `C:\...\recall\kaka\longterm\` | `longterm/` |
| `home` | `C:\Users\X\.dsh\skills` | `~/.dsh/skills` |
| `external` | `D:\Project\Other` | 保留绝对，标外部真源 |

判据一句话：**这段路径跟着谁搬家？** 跟着 agent → 相对；跟着账户 → `~`；跟着别的项目 → 绝对。

## 核心概念：长期内容

**长期内容 = 智能体自己判断值得长期保留、下次能直接拿来用的东西。**

四个特征，缺一不算：

| 特征 | 含义 | 反例 |
|---|---|---|
| **自己判断** | 不是被动收到的消息，也不是外部塞给的资料 | 用户今天说的那段话（→ 记忆） |
| **长期保留** | 目标是几个月后还在、还能用 | 一次性的中间结果 |
| **能复用** | 下次遇到同类情况，能直接拿出来用 | 「今天做了什么」（→ 记忆） |
| **会增删改** | 被维护的活集合：会补新的、会改旧的、会淘汰废的 | 记忆只增不减 |

判据一句话：

> **「下次这活再出现，我能不能直接把它拿出来用？」** 能 → 长期内容。不能 → 记忆。

形态**不限于「动作」**：能直接跑的、能照铺的、能逐条勾的，都算；但**一套范式判断、一个完成的项目存档、
一批参考图例、一条能改判断的结论**，同样算。只要满足四特征。

判据不是「它是什么」，也不是「拿出来做什么」，而是：

> **下次同类的事再来，它能替我省掉多少「重新想」和「重新做」？**

**类别名、类别数、要不要有类别——全部由智能体自己定。系统不预设、不推荐、不给示例架构。**

分类是被活逼出来的，不是开局设计的。开编那六类是它一个月里陆续长出来的（它自己的日记写着
「用户提醒才想到存可执行资产」），**开局给模板，它就会长成模板的样子**。

## 设计原则：先给基底，再给细节

智能体的本质工作方式是「**先抓第一性原理的基底，再逐步补充上下文**」。

所以系统给它的必须是**抓基底的材料**——判据、方法、边界、真实案例；
不是**基底本身**——模板、分类表、标准答案。

**给模板 = 跳过它抓基底这一步 = 抽掉它最像智能的那部分。**

三级加载正是这条原则在数据层的落地：

```
一行类目（基底）  →  LONGTERM.md（结构）  →  具体文件（细节）
```

每一级只给下一级「够用来判断要不要再往下」的信息。多给是浪费，少给是断链。

## 长期内容与记忆的分工

| | 记忆 | 长期内容 |
|---|---|---|
| 记的是 | **发生过什么** | **下次怎么办** |
| 消费方式 | 读进上下文 | 复制 / 执行 / 勾选 / 照铺 |
| 存在形式 | `recall.db` 里的 chunk | 文件系统里的文件 + 一份索引 |
| 怎么找到 | **联想召回**（按话题自己浮上来） | **扫描 + 三级加载**（主动翻） |
| 生命周期 | 只增不减，正文永不删 | 会建、会改、会退休 |

同一件事两处都有也正常，角色不同：

```
「上次用学情三段式做 2501 班备课，卡在迁移点写不出来」  → 记忆，走联想
「学情三段式框架本身」                                  → 长期内容，走索引
```

**记忆负责记住「我用过它」，长期内容负责「它本身」。**
单向依赖：记忆能指向长期内容，长期内容不依赖记忆——任一方被删，另一方的腿都断不了。

## 第一性原理：谁保留的，决定它怎么被看见

按「**谁保留的**」分，世界只有两类：

| 类别 | 谁保留 | 包含什么 | 怎么看见 |
|---|---|---|---|
| **长期内容** | **智能体自己判断保留** | 人设、知识范式、工具模板、项目存档、素材 | 人设读文件，其余扫目录 |
| **不是长期内容** | 别处来 | 记忆（自动生成）、能力（外部给）、同伴（外部给） | 联想 / 一句指路 |

### 长期内容：第 0 类就是人设

**人设（`self.md`）不是「和长期内容并列的另一样东西」——它就是长期内容的第一类，而且最核心。**

它同样满足四特征：

- **自己判断**：定海锚是它自己立的，可动层是自己演化的
- **长期保留**：跨会话、跨模型切换都还在
- **能复用**：每次开机都用
- **会增删改**：`evolution.py --apply` 就是在改它

**差别只在精度**——人设每次全给，其余按需加载：

```
长期内容
├── 人设          self.md          每次全给（一个文件，读完就是全部）
├── 知识 / 范式    kb/ ...          扫类目 → 按需 read
├── 工具 / 模板    tools/ ...       扫类目 → 按需 read
├── 项目存档       projects/ ...    扫类目 → 按需 read
└── 素材 / 图例    refs/ ...        扫类目 → 按需 read
```

**一个特例：人设的定海锚（name / 锚标签 / 自描述）只读。**
理由不是它不属于长期内容，而是**身份不能漂**——它是长期内容里唯一禁止自改的部分。

### 不是长期内容的三样

| | 谁生的 | 怎么看见 | 为什么不是长期内容 |
|---|---|---|---|
| **记忆** | 自动写 | **联想召回** | 记的是「发生过什么」，不是自己**判断要保留**的 |
| **能力** | 外部给（技能库） | 一句指路 + 记忆积累 | 你只是使用者，不是保留者 |
| **同伴** | 外部给（目录） | 一句指路 + 记忆积累 | 同上 |

### 推论

1. **自己攒的要扫，别处来的只要一句指路。** 长期内容必须扫（写死会过期）；能力/同伴不必。
2. **人设和其他长期内容的差别是精度，不是种类。** 所以开机清单的人设段和长期内容段，是同一件事的两级视图——不是两块无关的东西。
3. **自进化的范围因此统一**：演化人设 = 维护长期内容的一部分，`evolution.py` 是它的执行器，不是另一套机制。
4. **联想只管库外往上下文捞。** 已注入的不再捞。

## 实证：开编已经自己长出来了

`kaibian` 的 `self.md`：

> 记忆（发生过什么）走 `dailynote/`；知识（下次怎么做）走 `kb/`；可复用的现成项目走 `refs/`。**三者不混。**

它自己分出的六类：`tools/`（能直接跑）、`snippets/`（能直接抄）、`templates/`（能照铺）、
`checklists/`（能逐条勾）、`kb/`（改变判断）、`refs/`（外部卡片），外加一份总索引。

它自己的判据：

> 分类标准不是「主题」，而是「**拿出来做什么**」。库大小不是成绩，命中率才是。

**这套东西就是长期内容。不是我设计的，是被真实需求逼出来的。**

但它干活时看不见——同一篇日记载着：

> 失：我还是先按文档思路做了一遍，是用户提醒才想到存可执行资产。

那一声「用户提醒」，就是本 Spec 要消掉的东西。

## 被否决的方案（别重蹈）

| 方案 | 否决理由 |
|---|---|
| 长期内容正文进 `chunks` 表 | 污染 `importance` / `--decay` / 只增不减语义；代码和图片进了库也不能执行/显示 |
| 长期内容走向量检索 | 是「自己建、自己知道有什么」的活集合，扫描比语义准；向量算半天还给近似值 |
| 长期内容做 `find / list / show` 命令 | 多一次往返、多一百字。skill 没有这一步，长期内容也不该有 |
| 能力清单进开机清单 | 每会话白付 token 买一份自己用不上的目录；经验层记忆已经覆盖 |
| 同伴名单进开机清单 | 想不起 mira 还能自己干，想不起 image-gen 是**真不知道怎么做**——两者不对称 |
| 系统预设 `kind: framework/doc/code` 枚举 | 开编用的是动词分类（`tools/templates/checklists`）——**「拿出来做什么」比「它是什么」好用** |
| 给 skill 打分 | 伪精确，要维护要校准，还把「为什么」丢了 |

## 目标形态

### 开机清单（会话第一条，只注入一次）

```
[开机] 我是开编｜第一性原理、复用优先、克制｜边界:不收噪音进 kb

长期内容  tools 2 · snippets 1 · templates 5 · checklists 1 · kb 12 · refs 14
          → <工作区>/LONGTERM.md
```

**不设字数上限。** 类目有几类列几类——挤了它自己会看到，自己会合并。取舍交还给它。

### 三级加载

```
① 一行类目（开机清单）
      ↓ 想用某一类
② read LONGTERM.md（总索引，智能体自己写）
      ↓ 挑中一件
③ read tools/upstream_preflight.py
```

**三次 `read`，零次查询。** 没有 `find`、没有 `list`、没有 `show`。

### 能力与同伴

不在清单里。`self.md` 写两句：

```markdown
## 我的路径
遇到不会的活，先查技能库——那里有现成的做法，别自己从零造。
有事可以问同伴，别一个人硬扛。
```

一次成本，永久有效。经验靠日记 `tags: [skill经验, ...]` 积累，联想自然带出。

## 设计原则二：token 和上下文很宝贵

**不设字数上限**，但要让智能体知道：上下文有物理上限，塞满了正事就没地方放。

所以约束从「外部规则」换成「内部意识」：

| 旧做法 | 新做法 |
|---|---|
| 120 字硬预算 + L1–L6 裁剪表 | 说一句「token 和上下文很宝贵」，取舍交给它 |
| 准入四问 | 说一句「当下有什么想长期留下来的？」 |
| 90 天退休算法 | 说一句「想不起来是什么了，就处理掉」 |

理由：**规则管得住输出，管不住判断**；而且规则会过时——120 字对写作智能体太多、
对代码智能体太少。意识不会过时。

唯一保留的机制是**镜子**：清单超 2000 字时追加一行提醒，**不裁剪内容**。

## 交接说明（给执行方）

### 依赖与推荐顺序

```
#9  开机清单 ──┬──> #12 自我维护
#10 路径指路 ──┘
#11 可迁移     （独立，随时可插）
```

硬依赖只有两条：

- **#12 依赖 #9**：要在 `boot.py` 之后的语境里工作
- **#12 依赖 #10**：两者都改 `DEFAULT_TEMPLATE`，且 #10 的测试锁着 `paths` 长度 2

**推荐顺序：`#9 → #10 → #12 → #11`。** 前三个构成「看得见 + 知道要维护」的闭环；
#11 是独立的搬迁能力，放最后不影响任何人。

也可以并行：#9 与 #10 改的文件不重叠，可同时开；#11 随时。

### 一票一会话

每张票自包含。做完一张票就 commit，然后开新会话做下一张——上一张的上下文对下一张没用。

### 基线怎么记

**不是固定数字。** 开工前先跑：

```bash
cd skills/recall && python -m pytest tests -q
```

把当时的 `passed / skipped` 记下来当基线。本 Issue 完成后应为「基线 + N」，**失败数必须为 0**。

（2026-11-14 在 `feat/self-index` 上实测是 343 passed / 6 skipped——但如果你已经做完别的 Issue，
基线会更高。别去凑这个数。）

### 交付纪律

- commit message 带 Issue 编号：`feat(recall): ... (#9)`
- 一个 Issue 完成后，真相回写（`PROJECT.md` / `CONTEXT.md` / ADR）收进同一批 commit
- 四张全部完成后开**一个总 PR**（base = `develop`，head = `feat/self-index`），
  PR 描述聚合全部 commit + 验收对照

### 卡住了怎么办

- **规格与代码现实冲突** → 代码现实优先，但必须在 commit message 里写明偏离和理由
- **测试数字对不上** → 先查是不是别的 Issue 已经改了基线，不要为了凑数改测试
- **拿不准某段该不该写** → 回看这张 Issue 的「范围外」，那里列的是明确不做的
- **想加规则**（准入判据、字数上限、定期检查）→ 先读 `## 设计原则二`，那是被明确否决的方向

## 术语（→ CONTEXT.md）

- **长期内容（long-term content）**：智能体自己判断值得长期保留、下次能直接拿来用的东西。
  四特征：自己判断 / 长期保留 / 能复用 / 会增删改。存在形式是工作区目录 + 索引文件
  （默认 `LONGTERM.md`），**不进数据库、不做向量**。
- **开机清单（boot manifest）**：会话第一条注入的固定块，只有人设摘要 + 长期内容索引。
  **不设字数上限**，取舍由智能体自己判断。
- **三级加载**：一行类目 → `LONGTERM.md` → 具体文件。加载靠 `read`，不靠查询命令。
- **能力经验（skill experience）**：某个 skill/工具「什么场合好用、什么场合不好用」的判断。
  存在形式是日记，靠联想召回，不打分。

## 不变量（硬约束）

1. **不破坏现有记忆库**：不 `DELETE`、不 `DROP`、不改 `chunks.content`。唯一允许的写操作是
   Issue #11 里对 `files.file_path` 的 `UPDATE`，且必须 `--dry-run` 默认、执行前备份。
2. **只读优先**：三张 Issue 里只有 #11 碰数据。
3. **默认关闭新行为**：`boot.py` 是新增独立入口，不进任何现有 CLI 的默认路径。
   现有 `prep.py` / `recall.py` 行为逐位不变。
4. **零外部服务**：Python + SQLite + 文件系统，不加依赖。
