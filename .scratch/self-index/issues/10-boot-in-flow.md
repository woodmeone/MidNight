# 10 — 开机流程接入 boot.py（能力有了，没接上）

Issue: #19 ｜ Spec: `../spec.md` ｜ Blocked by: #9 ｜ 分支: `feat/self-index`

> 本文件自包含。**这是整个 feature 最后一处断链**：
> `boot.py` 造好了、测过了、能用，但**没有任何流程会去跑它**。

---

## 缺陷

`SKILL.md` 的「触发条件」表（56-71 行）是智能体行为的唯一指令来源。它写着：

| 触发词/情境 | 操作 |
|---|---|
| **每次回复用户前**（默认行为） | 运行 `prep.py ...` |
| 新会话开始 | 运行 `prep.py` 带时间连续性 |

**「新会话开始」教的是 `prep.py`，不是 `boot.py`。**

`boot.py` 在全文中只出现 5 次，全在「长期内容维护」和「体检」上下文里：

```
157  能力与同伴为什么不进开机清单（见 boot.py）
188  想看全文：python boot.py --identity <名字> --show-paths
233-235  体检三行
```

**没有一处说「开机时跑它」。**

### 实测后果

一个刚醒来的智能体，按文档做完这些：

1. 声明身份（`--identity`）
2. 跑 `prep.py` 召回最近记忆

它拿到的只有「最近聊过什么」。**它依然不知道自己有 18 件长期内容、不会的活该去哪查。**
`boot.py` 的能力等于不存在。

这和当初 `session_start.py` 的病一模一样——**零件有，没装上。**

---

## 用户故事

作为**一个新会话里的智能体**，我想要在说第一句话之前就知道「我是谁 + 我手里有什么」，
以便不用等到碰壁才想起自己有工具。

---

## 实现规格

### 改动一：触发条件表加「开机」这一行

在「新会话开始」那行之前插入：

```markdown
| **会话第一条消息之前**（开机，每次会话一次） | 运行 `boot.py --identity <我的名字>`，把输出当**已知背景**（不必贴给用户）。拿到「我是谁 + 长期内容类目 + 索引路径」三样 |
```

并把「新会话开始」那行改成：

```markdown
| 新会话开始（开机之后） | 运行 `prep.py` 带时间连续性，补最近发生了什么 |
```

### 改动二：新增一节「开机顺序」

放在「## 身份绑定」**之前**，因为开机要先用身份：

```markdown
## 开机顺序（会话第一条消息之前，一次）

**① 我是谁** —— 确定 `--identity`（见「身份绑定」）。

**② 我有什么** ——

```bash
python boot.py --identity <我的名字> [--workspace <当前工作区>]
```

拿到三样：

| 拿到什么 | 用途 |
|---|---|
| 人设摘要（我是谁 / 风格 / 边界 / 路径占位） | 说话的分寸 |
| 长期内容类目 + 计数 | **知道自己手里有什么**，别从零造 |
| `LONGTERM.md` 路径（含「根」） | 三级加载的第二级入口 |

输出当**已知背景**用，不必贴给用户。它是给你看的。

**③ 发生过什么** —— 每轮（含第一轮）跑 `prep.py`（见「触发条件」）。

### 两次调用分工

| 命令 | 什么时候 | 回答什么 |
|---|---|---|
| `boot.py` | **一次**，会话开头 | 我有什么 |
| `prep.py` | **每轮** | 这轮话题像哪段历史 |

开机清单每轮都贴会白烧 context——它一次就够，之后靠 `[回忆]`。
```

### 改动三：说明「没接 hook 时怎么办」

```markdown
> **没有 harness hook 时**：本 skill 只能**教**你在会话开头跑一次 `boot.py`，
> 不能强制。如果你的 harness 支持 session-start hook，把它挂在那儿更可靠——
> 那时这条纪律就从「记得跑」变成「自动跑」。
```

### 改动四：文件结构里点明 boot.py 的角色

`#17` 会重写文件结构。这一处由 `#17` 覆盖，本 Issue 不重复改，
但验收时要确认 `boot.py` 那行写的是「**开机清单**（三级加载第一级）」而不是光秃秃的文件名。

---

## 为什么不是「合并进 prep.py」

考虑过三个方案：

| 方案 | 取舍 |
|---|---|
| **A. 触发条件表加一行（采纳）** | 零代码，只改文档。缺点：靠 AI 自觉 |
| B. `prep.py --boot` 合并输出 | 少一个命令，但门控逻辑（`should_recall`）和开机清单是两件事——前者按消息内容判断要不要查，后者无条件给一次。合并会让 `prep_for_reply` 变复杂，且破坏它「与运行时无关的纯编排」定位 |
| C. 挂 harness session-start hook | 最可靠，但**超出 skill 范围**——skill 装不进别人的 harness 生命周期 |

**采纳 A**，并在文档里点明 C 是可选增强。理由：skill 是**指令**，不是运行时；
它能做的是把纪律写清楚，做不到替 harness 决定何时调用。
