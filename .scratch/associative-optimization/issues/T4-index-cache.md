# T4 · 召回性能：倒排/FTS 索引 + 结果缓存

**Blocked by**: T1
**Spec**: P3（堵评论区痛点③）

## 做什么
- 现状每次召回都：`recall()` 加载**全部 chunk 向量**逐条算余弦（O(#chunks)）+ `activate_tags()` 对**所有 tag** 向量算相似（O(#tags)）。
- 加：SQLite FTS/倒排索引做**候选预筛**（只扫"可能相关的一小摞"），+ 结果缓存（短时高频同查询直接命中）。

## 为什么（应用例子）
- **例**：监督一个学期后，张娜/熊可婷/马江波几十个学生 → 几百上千条日记。每次召回"全仓库从头算一遍"，越来越慢、越来越费。
  - **现状**：O(全部)扫描/次，越用越慢。
  - **改后**：先走 FTS 只挑含"张娜+升学+英语"的候选子集，再向量精排 → 记忆越多，召回仍快。
- **注意（防误读）**：注入量仍是 k 条（不爆），压的是**"找的过程"**，不是输出量。

## 关键设计
- 保持 `recall_associative` 接口不变；索引为底层实现，不影响结果语义。
- 缓存带时间窗 + 依赖失效（每次 ingest 后清相关缓存）。

## 验收
- 已有测试全绿。
- 指标用例：在含 N 条的记忆库上，召回耗时不随 N 线性增长（或显式标注为独立性能 ticket）。
- 正确性不回归：FTS 预设筛后仍能命中 tag-first 要求的核心候选（与 T1 集成回归）。
