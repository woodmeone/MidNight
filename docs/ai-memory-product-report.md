# AI 长期记忆产品方案调研报告

> 写给决策者 / 非纯技术读者。目标：帮你判断——Midnight Skills 这套 AI 记忆，下一步该做成什么形态、怎么设计触发、要不要服务器、要不要 SaaS。
> 写作要求：大白话 + 具体例子，少术语。
> 日期：2026-08-27（部分一手来源待后台调研补强，但方向性结论已可作选型依据）

---

## 一、先用一个贯穿全文的比喻

想象你的 AI 是《红楼梦》里照料贾宝玉的贴身丫鬟 **袭人**——她负责记得关于宝玉的一切小事。

给她"装记忆"，有三种做法。后面所有技术讨论都回到这个比喻。

| 做法 | 一句话 | 你会看到的现象 |
|---|---|---|
| **甲 VCP 式** | 每开口前把宝玉一生所有事背一遍 | 不忘事，但脑子永远塞爆、分不清当下 |
| **乙 纯 skill 式** | 宝玉不问，她就不想 | 她"不知道自己记得啥"，所以常常愣住答不上 |
| **丙 分层记忆式** | 桌上只放当下几页，其余存身后书库，靠"书名目录"按需取 | 脑子清爽，又"知道自己有哪些本"能去哪查 |

**你（用户）在几轮对话里独立推导出来的"第 3 点"——"只保留核心上下文，其他藏起来"——正是做法丙的核心。这个直觉是对的，而且已经是业界成熟范式的主流方向。**

## 二、三种触发架构逐个讲清楚（带例子）

### a. VCP 式：每轮全量注入记忆

**它是什么**：服务器在每次把请求发给模型之前，主动检索一遍记忆库，把找到的相关记忆全部塞进上下文，再发出去。AI 不需要"想不想回忆"，服务端替你回忆了。

**为什么这么做**：VCP 的作者认为——AI 有个死结，**"它不记得的东西，怎么会想到要去回忆它？"**（白皮书原话，你之前也引用过）。为了破这个死结，它选择了"别让 AI 决定，服务端一律先查一遍"。

**怎么用**：这就是你部署 C 盘那套 recall.db + 每轮进上下文的方式。

**优点**：永不忘事、不会出现"不知道去哪查"的死结。

**缺点（很关键）**：**上下文会被噪音塞爆**。模型一次能"同时在想"的量是有上限的（上下文窗口）。每轮全量灌注，等于让它脑子里同时响着几十件事，回应当下那句时就容易"分心"、漏重点、甚至答非所问。
- 例子：宝玉随口说"今天桂花开得不错"，做法甲也会触发袭人去翻"桂花"相关的旧记忆——哪怕那句话毫无查讯息的意义。

**结论**：可靠性高，但"健忘"换来了"塞爆大脑"。**不符合脑的规律**（下面第 4 节讲为什么）。

---

### b. 纯 skill 式：AI 自觉触发（你现在 Midnight 的做法）

**它是什么**：AI 从上下文里读到一段"触发条件"（SKILL.md 里写"当用户说记住/还记得我吗/帮我回忆时用"），然后**自己决定**什么时候去查记忆、查什么。

**为什么这么做**：skill 没有服务端钩子，拿不到"每轮无条件执行"的入口，只能靠 AI 读了规则后自觉调用（像 Claude Code / Cursor 这类 Agent 工具的做法）。

**怎么用**：这就是现在 `/recall` 加一段触发描述、AI 读到触发词自己跑。

**缺点**：回到那个死结——**AI 得先"想起来"要查，才会去查；它想不起来，是因为它可能压根不知道自己记得。**
- 例子：三个月前你告诉它"我下个月考雅思"。现在你说"我压力好大"。它如果不记得"雅思"这事，就**不会主动**拿"压力"去检索——而"压力"其实能命中"雅思"的记忆。于是它就漏了。这就是**鸡生蛋**：不记得→不去查→永远想不起来。

**结论**：灵活、省 token、不像甲那么灌满，但**触发不可靠**，治不了那个"不知道自己记得"的毛病。

---

### c. 分层记忆 + 按需换页（MemGPT/Letta 式）—— 你的第 3 点正解法

**它是什么**：把记忆分成两层：
- 一层叫**主上下文（办公桌）**——只放"当前任务的少量内容"，保持很小、很清爽。
- 另一层叫**外部存储（书库）**——所有历史记忆全在这，平时不进上下文。
- 中间有一个**"索引/目录"**——AI 知道自己有哪些"卷宗/话题"，聊到哪个话题，才知道去外部存储"抽哪本"。

**为什么这么做（MemGPT 论文 arXiv:2310.08560 的出发点）**：模型有上下文窗口**上限**（像工作记忆有容量上限），但人类需要"似乎无限"的长期记忆（像海量终身记忆）。论文作者提出把模型当成一个有"内存分层"的操作系统——主上下文是"寄存/工作内存"，外部存储是"硬盘"，按需换页。**目的就是你说的：防止上下文过曝、注意力涣散，同时保留无限记忆。**

**怎么用**：
- 平时只给模型一小段"当前对话 + 少量最相关记忆"。
- 当话题切到"考试"该 AI 想起时，它通过目录知道"有考试这个卷宗"，去书库翻，把相关几段抽出来放桌上（塞进上下文）。
- 别的都不进上下文。上下文恒定、清爽。

**与乙的区别**：乙是靠 AI 凭空自觉；丙是给 AI 一份**"我知道自己有哪些记忆"的目录**。目录让"知不知道自己记得"这个问题被**显式解决**——它不是靠 AI 灵光一现，而是总能扫一眼自己有哪类记忆再决定调哪类。这**破解了鸡生蛋**，又不至于像甲那样把什么都灌进大脑。

**处理甲的问题**：甲灌满上下文造成的噪音/分心，丙不会发生，因为非当前话题的记忆根本不出现。

## 三、主流 AI 记忆产品到底怎么做（横向）

| 产品/项目 | 关键做法 | 放哪层 |
|---|---|---|
| **MemGPT / Letta** | 论文提出分层记忆，`RecallQueue`（会话摘要）+ `ArchivalMemory`（长期档案块）+ 主上下文。上下文先塞"关联程度高"的，满了把不相关的"换出"到外部 | 丙 |
| **Claude Code**（Anthropic 官方 Agent） | 务实中间派：工作区的会话持久记忆 + `CLAUDE.md` 常驻项目记忆 + 显式 `/memory`；不赌 AI 自觉找线索检索长尾 | 丙偏务实 |
| **SuperMemory**（29k star） | 用户主动往里存网页/笔记，做成独立记忆库 API，靠向量检索返回 | 强丙（但它是"人喂"，不是"AI 自记"） |
| **VCP**（你研究的对象） | 每轮服务端遍历预处理器全量注入记忆+工具 | 甲 |
| **Midnight Skills（当前）** | skill + 本地 SQLite，AI 自觉触发 | 偏乙（可演进到丙） |

**重要观察**：**目前没有成功产品走"甲"（每轮全量塞爆）路线**。主流都朝"分层 + 克制上下文"（丙）靠，因为大家都碰到同一个墙——上下文窗口有限，灌满必崩。

## 四、人类记忆：为什么"丙"最接近人脑（一手认知科学依据）

- **工作记忆容量有限**：Miller 1956 经典研究——人一次能"同时在线握住"的信息约 7±2 个组块。这跟你 AI 的上下文窗口上限本质是同一个东西：**一次装太多就顾不上当下**。这正是"丙 只留一点在桌上"的生物学理由。
- **人类不是时时全量检索**：日常对话你不会每句话前翻一遍终身记忆。你是**线索依赖提取（cued recall）**——某个词/场景/情绪触发时才想起相关记忆。丙的"目录 + 按需换页"模拟的就是这个。
- **记忆是重建不是回放**：你想起一件事，是把碎片重建出来的，不是录像回放。Retrieval 总是在某个**线索驱动**下发生，很少"无事自启"。
- **结论**：人脑= 有限工作记忆(桌上) + 海量长期记忆(书库) + 触发式提取。**丙 的结构**（精简上下文 + 外部存储 + 目录索引/线索）是离"自然智能"最近的工程近似。**甲 违背人脑**（把海量硬塞进有限的上下文）；乙 则漏了"目录"这一环（不知道有可提取的东西）。

## 五、结语与建议（针对「是否做 SaaS / 是否需要服务器」）

### 结论：方向上是"丙 + 目录"，不是"甲的复刻"

- 你的判断（第 3 点）：只留核心上下文，其余隐藏 → 对，而且有 MemGPT/Letta 背书。
- 追问什么时候触发（你的问题 1）：在"丙"里，靠的是 **目录 + 语义线索**（embedding 比对"现在这与哪本记忆相关"），既不是每轮全灌（甲），也不赌 AI 凭空自觉（乙）。

### 要不要服务器？

- **单机自用**：不需要。丙 的"外部存储"可以直接是本地 SQLite + 向量检索，skill 就能实现"目录 + 按需取"。
- **做 SaaS**：需要——因为多用户要隔离（多租户=每人一套分区）、要云端持久、要有 API 让用户在任意客户端调用。这时候服务器才有意义（本地 FastAPI + 云部署皆可，不必是 VCP 那种庞然大物）。

### 需不需要迁移到 VCP？

- **不需要，也不必主动迁**。你不做 VCP 复刻 → 现在的 64 篇 md + SQLite 结构（files/chunks/tags）在丙 架构里**照样能用**（它就是分层记忆的那个"书库"）。数据原地保留即可，将来要迁也容易（纯文本日记各处能导入）。
- 你担心"浪费 token"，**没有浪费**：这几轮讨论已经把你从"甲路线 或 VCP 路线"拉回"丙路线 + 是否上多租户服务器"这个更正确的选型路径上。
